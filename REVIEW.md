# Критерии ревью

Единый источник критериев для независимого авторевью pull request
([`.github/workflows/review.yml`](.github/workflows/review.yml)) и для
человека-ревьюера. Ревьюер смотрит только diff PR и не меняет код.

## 1. Соответствие задаче

- PR ссылается на issue: `Closes #n`, `Refs #n` или `Part of #n`.
- Изменение решает задачу из issue или спеки и не выходит за её рамки.
- Нет несвязанных правок, переформатирования «заодно» и переименований без
  причины.

## 2. Корректность и поведение

- Основной сценарий задачи работает, граничные случаи и ошибки обработаны.
- Новое поведение покрыто тестами на существующих швах.
- Тесты проверяют внешний результат, а не внутреннюю структуру.
- Негативный сценарий из спеки действительно ломает тест или CI.

## 3. Контракт и данные

- `contract/`, `contract/tsp-output/` и `frontend/src/api/generated/` не
  редактируются вручную: изменения только через `make generate`.
- Изменения API и схемы SQLite согласованы с ADR и не ломают существующих
  клиентов.
- Правила записи (часовой пояс, рабочие дни, слоты, окно записи) не меняются
  без явного требования.

## 4. Безопасность

- В коде, логах и тестах нет секретов, токенов и персональных данных.
- Workflow используют минимальные `permissions`.
- Пользовательский ввод валидируется, SQL-запросы параметризованы.
- Для pull request из форка секреты не передаются и привилегии не повышаются.

## 5. Качество кода

- Соблюдены слои из ADR 0006 и шов доступа к данным из ADR 0010.
- Нет дублирования логики, мёртвого кода и «магических» литералов.
- Имена отражают доменные понятия из [`GLOSSARY.md`](GLOSSARY.md).
- Ошибки соответствуют закрытому контракту из ADR 0008.

## 6. Документация

- README и ADR обновлены, если меняется поведение, конфигурация или workflow.
- Коммиты — Conventional Commits со ссылкой на тикет.

## 7. Риск и откат

- В PR заполнены разделы «Проверки», «Риск» и «Откат».
- Указано, что затронуто: API, данные, конфигурация, UI, зависимости.
- Откат реален: `git revert` или revert PR, обратимость миграций, отсутствие
  потери данных.

## Формат вывода авторевью

Каждый комментарий начинается маркером `<!-- opencode-auto-review -->` и имеет
вид:

```markdown
## Авторевью

### Блокирующие

- `path/to/file.ts:42` — что не так и что исправить.

### Неблокирующие

- `path/to/file.ts:17` — замечание.
```

Если блокирующих замечаний нет, это пишется явно. Пустой комментарий и
пересказ diff недопустимы.
